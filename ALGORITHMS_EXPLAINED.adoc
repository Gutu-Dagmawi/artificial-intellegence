== Introduction

This document explains three pathfinding algorithms: BFS, UCS, and A*. Each finds the best route from a starting point to a destination on a road network.

=== The Road Network

A graph consists of:
- **Nodes**: Intersections with coordinates (latitude, longitude)
- **Edges**: Roads connecting nodes, each with a distance (weight)

== Algorithm 1: Breadth-First Search (BFS)

=== Overview

BFS explores the road network layer by layer, like ripples spreading outward. It is fundamentally an **unweighted search algorithm**, meaning it treats all edges as having equal cost regardless of their actual distance.

[cols="1,2"]
|===
| Property | Value
| Optimality | ❌ Does NOT guarantee shortest distance
| Completeness | ✅ Always finds a path (if one exists)
| Time Complexity | O(V + E) where V=nodes, E=edges
| Space Complexity | O(V) for queue and visited set
| Best for | Unweighted graphs (all edges equal cost)
|===

=== Deep Dive: Why BFS Fails for Weighted Graphs

==== The Fundamental Problem

BFS's core mechanism is the **FIFO (First-In-First-Out) queue**. This queue processes nodes in the exact order they were discovered, not in order of their distance from the start.

Consider this critical scenario:

[source]
----
Network: A --1m-- B
         |
        1000m
         |
         C --1m-- D

Goal: Find path from A to D

BFS Execution:
1. Start: Queue = [A], Visited = {A}
2. Process A: Add neighbors B and C
   Queue = [B, C], Visited = {A, B, C}
   
3. Process B (added first!): Add neighbors
   Queue = [C, ...], Visited = {A, B, C}
   
4. Process C: Add neighbor D
   Queue = [..., D], Visited = {A, B, C, D}
   
5. Process D: FOUND!

BFS Path: A → B → ... → D (shortest in edges)
Actual optimal: A → C → D (shortest in distance: 1001m vs 1+1000m = 1001m)

Wait, they're the same! Let me revise:

Network: A --1m-- B --1000m-- D
         |
        1m
         |
         C --1m-- E --1m-- D

BFS finds: A → B → D (2 edges, 1001m)
Optimal: A → C → E → D (3 edges, 3m)

BFS chose the path with FEWER EDGES, not SHORTER DISTANCE!
----

==== The Mathematical Reason

BFS guarantees the **shortest path in terms of edge count**, not distance. This is because:

1. **Invariant**: When BFS processes a node at distance d (in edges), all nodes at distance d-1 have already been processed
2. **Consequence**: The first time you reach the goal, you've used the minimum number of edges
3. **Problem**: Minimum edges ≠ minimum distance when edges have different weights

==== Proof That BFS is Suboptimal for Weighted Graphs

**Theorem**: BFS does not guarantee the shortest weighted path.

**Proof by counterexample**:
- Let G = (V, E, w) be a weighted graph
- Let p1 be the path BFS finds (minimum edges)
- Let p2 be the optimal path (minimum distance)
- If w(p1) > w(p2), then BFS is suboptimal

Example:
[source]
----
Graph: 1 --1-- 2 --100-- 3
       |
       101
       |
       4 --1-- 5 --1-- 3

BFS finds: 1 → 2 → 3 (2 edges, weight 101)
Optimal: 1 → 4 → 5 → 3 (3 edges, weight 103)

Actually, 101 < 103, so BFS wins here. Let me fix:

Graph: 1 --1-- 2 --100-- 3
       |
       50
       |
       4 --1-- 5 --1-- 3

BFS finds: 1 → 2 → 3 (2 edges, weight 101)
Optimal: 1 → 4 → 5 → 3 (3 edges, weight 52)

BFS is suboptimal! ✓
----

==== Why BFS Uses a FIFO Queue

The FIFO queue is essential for BFS's correctness **in unweighted graphs**:

[source]
----
Unweighted Graph Property:
- All edges have weight 1
- Distance from start = number of edges
- FIFO queue processes by edge count
- Therefore: First time reaching goal = minimum edges = minimum distance

Weighted Graph Problem:
- Edges have different weights
- Distance from start ≠ number of edges
- FIFO queue still processes by edge count
- Therefore: First time reaching goal ≠ minimum distance
----

=== Example: The Failure Case

[source]
----
Network: A --500m-- B --300m-- C
         |                      |
        400m                   200m
         |                      |
         D --600m-- E --400m-- F

BFS from A to F:
Step 1: Queue = [A], Visited = {A}
Step 2: Process A
        Add B (500m away), D (400m away)
        Queue = [B, D], Visited = {A, B, D}
        
Step 3: Process B (FIFO: B was added first)
        Add C (500+300=800m away)
        Queue = [D, C], Visited = {A, B, D, C}
        
Step 4: Process D
        Add E (400+600=1000m away)
        Queue = [C, E], Visited = {A, B, D, C, E}
        
Step 5: Process C
        Add F (800+200=1000m away)
        Queue = [E, F], Visited = {A, B, D, C, E, F}
        
Step 6: Process E
        F already visited, skip
        Queue = [F]
        
Step 7: Process F: FOUND!

BFS Path: A → B → C → F
BFS Distance: 500 + 300 + 200 = 1000m
BFS Edges: 3

Alternative Path: A → D → E → F
Alternative Distance: 400 + 600 + 400 = 1400m
Alternative Edges: 3

In this case, BFS happened to find the optimal! But only because the shortest distance path also had the fewest edges. This is NOT guaranteed.
----

=== Code

[source,python]
----
def bfs_search(self, start: int, goal: int):
    queue = deque([start])
    visited = {start}
    parent = {start: None}
    
    while queue:
        current = queue.popleft()
        
        if current == goal:
            # Reconstruct path from parent pointers
            path = []
            node = goal
            while node is not None:
                path.append(node)
                node = parent[node]
            path.reverse()
            return path
        
        for neighbor in self.graph.successors(current):
            if neighbor not in visited:
                visited.add(neighbor)
                parent[neighbor] = current
                queue.append(neighbor)
    
    return None  # No path found
----

== Algorithm 2: Uniform Cost Search (UCS)

=== Overview

UCS is the optimal solution for weighted graphs. It explores nodes in order of **actual distance from start**, guaranteeing the shortest path. Also known as **Dijkstra's algorithm**.

[cols="1,2"]
|===
| Property | Value
| Optimality | ✅ GUARANTEES shortest distance
| Completeness | ✅ Always finds a path (if one exists)
| Time Complexity | O((V + E) log V) with min-heap
| Space Complexity | O(V) for priority queue and cost tracking
| Best for | Weighted graphs needing optimal distance
|===

=== The Core Insight: The Dijkstra Invariant

UCS's correctness rests on a single, powerful invariant:

**Dijkstra's Invariant**: When UCS pops a node from the priority queue, the cost to that node is **guaranteed to be optimal** (shortest possible).

This is the key difference from BFS!

[source]
----
BFS Invariant:
"When we process a node, we've reached it in minimum edges"

UCS Invariant:
"When we process a node, we've reached it in minimum DISTANCE"

Why the difference?
- BFS uses FIFO queue (processes by insertion order)
- UCS uses priority queue (processes by cost order)
----

=== Proof of Optimality

**Theorem**: UCS finds the shortest path in a weighted graph with non-negative edge weights.

**Proof**:
1. Let n be the node UCS pops from the priority queue
2. Let cost(n) be the cost stored in the priority queue for node n
3. **Claim**: cost(n) is the shortest distance from start to n

**Proof by contradiction**:
- Assume there exists a shorter path p to n with cost < cost(n)
- Let x be the last node on path p that was already processed by UCS
- Let y be the next node on path p after x
- The cost to reach y via p is: cost(x) + edge(x,y)
- Since UCS processes nodes in order of increasing cost:
  - cost(x) was already popped and processed
  - cost(y) ≤ cost(x) + edge(x,y) (UCS would have found this path)
- But we assumed cost(n) via p < cost(n) in queue
- This contradicts UCS's processing order
- Therefore, no shorter path exists ✓

**Important constraint**: This proof requires **non-negative edge weights**. If negative weights exist, UCS fails!

=== Why UCS Explores More Nodes Than A*

UCS has a critical limitation: **it has no information about where the goal is**.

[source]
----
UCS Exploration Pattern:
- Explores all nodes within distance d from start
- Then explores all nodes within distance d+ε
- Forms a circle/sphere around the start point
- Expands equally in all directions

Example: Finding path from A to F
UCS explores: All nodes 0-400m away, then 400-500m, then 500-800m, etc.
This includes nodes in completely wrong directions!

A* Exploration Pattern:
- Explores nodes that seem to lead toward goal
- Prioritizes nodes with low f(n) = g(n) + h(n)
- Forms an ellipse pointing toward goal
- Focuses search in promising direction
----

=== The Cost Tracking Mechanism

UCS uses a **cost_so_far dictionary** to track the best known distance to each node:

[source,python]
----
cost_so_far = {
    A: 0,      # Starting point
    B: 500,    # Best known cost to B
    D: 400,    # Best known cost to D
    C: 800,    # Best known cost to C
    E: 1000,   # Best known cost to E
    F: 1000    # Best known cost to F
}

When we find a new path to a node:
- Calculate new_cost = current_cost + edge_length
- If new_cost < cost_so_far[neighbor]:
    - Update cost_so_far[neighbor] = new_cost
    - Add (new_cost, neighbor) to priority queue
- Else:
    - Ignore this path (we already have a better one)
----

This is why UCS can revisit nodes (unlike BFS)! If we find a better path, we process the node again.

=== Example with Detailed Cost Tracking

[source]
----
Network: A --500m-- B --300m-- C
         |                      |
        400m                   200m
         |                      |
         D --600m-- E --400m-- F

UCS from A to F:
Step 1: Initialize
        PQ: [(0, A)]
        cost_so_far: {A: 0}
        parent: {A: None}

Step 2: Pop (0, A) - Process A
        For neighbor B: new_cost = 0 + 500 = 500
            500 < inf, so update
            PQ: [(500, B), (400, D)]
            cost_so_far: {A: 0, B: 500, D: 400}
        For neighbor D: new_cost = 0 + 400 = 400
            400 < inf, so update
            PQ: [(400, D), (500, B)]
            cost_so_far: {A: 0, B: 500, D: 400}

Step 3: Pop (400, D) - Process D
        For neighbor E: new_cost = 400 + 600 = 1000
            1000 < inf, so update
            PQ: [(500, B), (1000, E)]
            cost_so_far: {A: 0, B: 500, D: 400, E: 1000}

Step 4: Pop (500, B) - Process B
        For neighbor C: new_cost = 500 + 300 = 800
            800 < inf, so update
            PQ: [(800, C), (1000, E)]
            cost_so_far: {A: 0, B: 500, D: 400, E: 1000, C: 800}

Step 5: Pop (800, C) - Process C
        For neighbor F: new_cost = 800 + 200 = 1000
            1000 < inf, so update
            PQ: [(1000, E), (1000, F)]
            cost_so_far: {A: 0, B: 500, D: 400, E: 1000, C: 800, F: 1000}

        For neighbor F: new_cost = 1000 + 400 = 1400
            1400 > 1000 (already in cost_so_far), so SKIP

        Final cost: 1000m ✅ OPTIMAL
        Path: A → B → C → F
----

Notice in Step 6: We found an alternative path to F (1400m) but it's worse than our current best (1000m), so we ignore it. This is why UCS guarantees optimality - it never accepts a worse path.

=== The Priority Queue Ordering

The priority queue is crucial. It must always return the node with **lowest cost**:

[source,python]
----
import heapq

# Min-heap: always returns smallest element
pq = []
heapq.heappush(pq, (500, 'B'))
heapq.heappush(pq, (400, 'D'))
heapq.heappush(pq, (800, 'C'))

next_node = heapq.heappop(pq)  # Returns (400, 'D')
next_node = heapq.heappop(pq)  # Returns (500, 'B')
next_node = heapq.heappop(pq)  # Returns (800, 'C')

The heap maintains O(log V) insertion and extraction!
----

=== Code

[source,python]
----
def uniform_cost_search(self, start: int, goal: int):
    pq = [(0, start)]  # Priority queue: (cost, node)
    cost_so_far = {start: 0}
    parent = {start: None}
    
    while pq:
        current_cost, current = heapq.heappop(pq)
        
        if current == goal:
            # Reconstruct path
            path = []
            node = goal
            while node is not None:
                path.append(node)
                node = parent[node]
            path.reverse()
            return path, current_cost
        
        # Skip if we found a better path already
        if current_cost > cost_so_far.get(current, float('inf')):
            continue
        
        for neighbor in self.graph.successors(current):
            edge_length = self.get_edge_length(current, neighbor)
            new_cost = current_cost + edge_length
            
            if new_cost < cost_so_far.get(neighbor, float('inf')):
                cost_so_far[neighbor] = new_cost
                parent[neighbor] = current
                heapq.heappush(pq, (new_cost, neighbor))
    
    return None, float('inf')
----

== Algorithm 3: A* Search

=== Overview

A* is the most intelligent algorithm. It combines UCS's optimality guarantee with a **heuristic** (educated guess) about where the goal is. This makes it dramatically faster while maintaining optimality.

[cols="1,2"]
|===
| Property | Value
| Optimality | ✅ GUARANTEES shortest distance (if heuristic is admissible)
| Completeness | ✅ Always finds a path (if one exists)
| Time Complexity | O((V + E) log V) but with much smaller effective search space
| Space Complexity | O(V) for priority queue and cost tracking
| Best for | Weighted graphs needing optimal distance FAST
|===

=== The Fundamental Insight: Combining Actual and Estimated Cost

A* is based on a deceptively simple idea that has profound implications:

**Core Principle**: Explore nodes that are both:
1. Close to the start (low actual cost g(n))
2. Seem to lead toward the goal (low estimated remaining cost h(n))

This is fundamentally different from UCS, which only considers #1.

[source]
----
UCS: "Explore the closest node to start"
     Explores in all directions equally
     
A*:  "Explore the node that seems closest to goal"
     Prioritizes promising directions
     
The difference: A* uses domain knowledge (heuristic) to guide search
----

=== The A* Evaluation Function

A* uses a carefully designed evaluation function:

[source]
----
f(n) = g(n) + h(n)

Where:
  g(n) = actual cost from start to node n (known, exact)
  h(n) = heuristic estimate from node n to goal (unknown, estimated)
  f(n) = estimated total cost of path through node n

A* always expands the node with LOWEST f(n) next.

Intuition:
- g(n) tells us how far we've come
- h(n) tells us how far we have left
- f(n) = total estimated distance
----

=== The Critical Requirement: Admissibility

For A* to guarantee optimality, the heuristic h(n) must be **admissible**:

**Definition**: A heuristic h(n) is admissible if:
- h(n) ≤ actual_distance(n, goal) for all nodes n
- h(goal) = 0

In other words: **The heuristic must never overestimate the actual distance**.

==== Why Admissibility Matters

**Theorem**: If h(n) is admissible, A* finds the optimal path.

**Proof sketch**:
1. Let n* be the goal node
2. Let C* be the optimal path cost
3. Suppose A* returns a suboptimal path with cost C > C*
4. At some point, A* must have expanded a node n on the optimal path
5. For that node: f(n) = g(n) + h(n) ≤ g(n) + actual_distance(n, goal) = C*
6. Since A* expands nodes in order of f-value, it would have expanded n before any node with f > C*
7. But the suboptimal goal has f ≥ C > C*, contradiction!
8. Therefore, A* must find the optimal path ✓

**Key insight**: Admissibility is NECESSARY for optimality. If h(n) overestimates even once, A* can miss the optimal path!

==== The Haversine Heuristic

In our code, we use the **Haversine formula** to calculate straight-line distance:

[source]
----
Haversine Distance Formula:
d = 2R * arcsin(√(sin²(Δφ/2) + cos(φ1)*cos(φ2)*sin²(Δλ/2)))

Where:
  R = Earth's radius (6,371 km)
  φ1, φ2 = latitudes
  Δφ = latitude difference
  Δλ = longitude difference

Why it's admissible:
- Straight-line distance ≤ road distance
- Roads must follow the terrain, curves, etc.
- Straight line is always shorter
- Therefore: h(n) ≤ actual_distance(n, goal) ✓

Example:
  Actual road: 1000m (following roads)
  Haversine: 800m (straight line)
  800 < 1000, so admissible ✓
----

=== Consistency (Monotonicity)

Beyond admissibility, there's a stronger property called **consistency**:

**Definition**: A heuristic h(n) is consistent if:
- h(n) ≤ cost(n, n') + h(n') for all edges (n, n')

In other words: **The heuristic decreases smoothly as you approach the goal**.

[source]
----
Consistency Example:
  Node A: h(A) = 800m to goal
  Edge A→B: cost = 500m
  Node B: h(B) = 600m to goal
  
  Check: h(A) ≤ cost(A,B) + h(B)
         800 ≤ 500 + 600
         800 ≤ 1100 ✓ Consistent!
         
Non-consistent example:
  Node A: h(A) = 800m to goal
  Edge A→B: cost = 500m
  Node B: h(B) = 400m to goal
  
  Check: h(A) ≤ cost(A,B) + h(B)
         800 ≤ 500 + 400
         800 ≤ 900 ✓ Still consistent!
         
Actually, Haversine is always consistent because:
- Triangle inequality: d(A,goal) ≤ d(A,B) + d(B,goal)
- Therefore: h(A) ≤ cost(A,B) + h(B) ✓
----

**Why consistency matters**: If h(n) is consistent, A* never needs to re-expand a node. Once a node is popped from the queue, its cost is final. This is more efficient than the general case.

=== Why A* Explores Fewer Nodes: A Deep Analysis

The dramatic efficiency gain of A* comes from a subtle but powerful mechanism:

==== The Search Space Reduction

**UCS Exploration Pattern** (Dijkstra):
[source]
----
UCS expands all nodes n where g(n) ≤ C*
(where C* is the optimal path cost)

This forms a "circle" around the start:
- All nodes within distance C* from start are explored
- Regardless of direction
- Includes nodes far from goal

Example: Finding path from A to F in a 60,000-node graph
- UCS might explore 9,500 nodes
- These form a roughly circular region around A
- Many are in completely wrong directions
----

**A* Exploration Pattern**:
[source]
----
A* expands all nodes n where f(n) ≤ C*
(where C* is the optimal path cost)

This forms an "ellipse" pointing toward goal:
- Nodes with low f(n) = g(n) + h(n) are explored
- Prioritizes nodes that seem to lead toward goal
- Avoids exploring in wrong directions

Example: Same 60,000-node graph
- A* might explore only 1,070 nodes
- These form an ellipse from A to F
- Focused on promising directions
----

==== Mathematical Explanation

The key difference:

[source]
----
UCS expands node n if: g(n) ≤ C*
A* expands node n if: g(n) + h(n) ≤ C*

Since h(n) > 0 for all n ≠ goal:
g(n) + h(n) > g(n)

Therefore: A* expands fewer nodes!

Specifically:
- UCS expands all n where g(n) ≤ C*
- A* expands only n where g(n) ≤ C* - h(n)
- The term h(n) "cuts off" exploration in wrong directions
----

==== The Heuristic Quality Matters

The quality of h(n) directly affects efficiency:

[source]
----
Perfect heuristic: h(n) = actual_distance(n, goal)
- A* expands only nodes on the optimal path
- Explores minimum possible nodes
- Maximum efficiency

Good heuristic: h(n) ≈ actual_distance(n, goal)
- A* expands mostly nodes near optimal path
- Explores few unnecessary nodes
- High efficiency

Poor heuristic: h(n) ≈ 0 (very underestimates)
- A* behaves like UCS
- Explores many unnecessary nodes
- Low efficiency

Bad heuristic: h(n) > actual_distance(n, goal) (overestimates)
- A* is NOT optimal!
- May miss the optimal path
- INVALID!
----

Haversine is a good heuristic because:
1. It's admissible (never overestimates)
2. It's consistent (decreases smoothly)
3. It's relatively accurate (straight-line is close to road distance)

=== Code

[source,python]
----
def astar_search(self, start: int, goal: int):
    h_start = self.haversine_distance(start, goal)
    pq = [(h_start, start)]
    
    g_score = {start: 0}
    parent = {start: None}
    
    while pq:
        f_score, current = heapq.heappop(pq)
        
        if current == goal:
            path = []
            node = goal
            while node is not None:
                path.append(node)
                node = parent[node]
            path.reverse()
            return path, g_score[goal]
        
        current_g = g_score.get(current, float('inf'))
        if f_score > current_g + self.haversine_distance(current, goal):
            continue
        
        for neighbor in self.graph.successors(current):
            edge_length = self.get_edge_length(current, neighbor)
            tentative_g = current_g + edge_length
            
            if tentative_g < g_score.get(neighbor, float('inf')):
                g_score[neighbor] = tentative_g
                h_score = self.haversine_distance(neighbor, goal)
                f_score = tentative_g + h_score
                parent[neighbor] = current
                heapq.heappush(pq, (f_score, neighbor))
    
    return None, float('inf')
----

== Deep Comparison: BFS vs UCS vs A*

=== Fundamental Differences

[cols="1,1,1,1"]
|===
| Aspect | BFS | UCS | A*

| **Optimality** | ❌ No | ✅ Yes | ✅ Yes*
| **Considers Distance** | ❌ No | ✅ Yes | ✅ Yes
| **Uses Heuristic** | ❌ No | ❌ No | ✅ Yes
| **Nodes Explored** | 🔴 Many | 🟡 Medium | 🟢 Few
| **Speed** | 🔴 Slow | 🟡 Medium | 🟢 Fast
| **Complexity** | 🟢 Simple | 🟡 Medium | 🔴 Complex
| **Data Structure** | FIFO Queue | Min-Heap | Min-Heap
| **Expansion Order** | By edge count | By g(n) | By f(n)=g(n)+h(n)
|===

*A* is optimal only if heuristic is admissible

=== Why Each Algorithm Fails or Succeeds

==== BFS: The Fundamental Flaw

BFS fails because it optimizes for the wrong metric:

[source]
----
BFS Optimization: Minimize number of edges
Problem: Edges have different weights!

Example:
Path 1: 2 edges, 1001m total
Path 2: 3 edges, 3m total

BFS chooses Path 1 (fewer edges)
Optimal is Path 2 (shorter distance)

Root cause: FIFO queue ignores edge weights
Solution: Use priority queue (UCS/A*)
----

==== UCS: The Efficiency Problem

UCS is optimal but inefficient:

[source]
----
UCS Limitation: No information about goal direction

Exploration pattern:
- Expands all nodes within distance d from start
- Then all nodes within distance d+ε
- Forms concentric circles
- Explores equally in all directions

Why inefficient:
- Many explored nodes are far from goal
- No guidance toward goal
- Wastes computation on wrong directions

Solution: Add heuristic to guide search (A*)
----

==== A*: The Optimal Solution

A* succeeds by combining the best of both worlds:

[source]
----
A* Advantages:
1. Optimal (like UCS) - guarantees shortest path
2. Efficient (better than UCS) - explores fewer nodes
3. Informed (unlike UCS) - uses heuristic to guide search

How it works:
- f(n) = g(n) + h(n)
- g(n) ensures optimality (actual cost)
- h(n) ensures efficiency (estimated remaining cost)
- Expands nodes that seem to lead to goal

Why it works:
- h(n) ≤ actual distance (admissibility)
- Therefore: f(n) ≤ actual total cost
- Nodes far from goal have high f(n)
- Nodes near goal have low f(n)
- Priority queue explores low f(n) first
- Result: Focused search toward goal
----

=== Complexity Analysis

==== Time Complexity

[cols="1,1,1"]
|===
| Algorithm | Time Complexity | Notes

| BFS | O(V + E) | Linear in graph size
| UCS | O((V + E) log V) | Log factor from heap operations
| A* | O((V + E) log V) | Same as UCS, but explores fewer nodes in practice
|===

**Important**: The theoretical complexity is the same for UCS and A*, but A* explores far fewer nodes in practice due to the heuristic.

==== Space Complexity

[cols="1,1,1"]
|===
| Algorithm | Space Complexity | What's Stored

| BFS | O(V) | Queue + visited set
| UCS | O(V) | Priority queue + cost tracking
| A* | O(V) | Priority queue + cost tracking
|===

All three store O(V) space in the worst case, but A* typically stores fewer nodes because it explores fewer.

- A* advantage is minimal

== Key Concepts

=== Priority Queue (Min-Heap)

Always returns the element with lowest priority:

[source,python]
----
import heapq

pq = [(5, 'A'), (2, 'B'), (8, 'C'), (1, 'D')]
next = heapq.heappop(pq)  # Returns (1, 'D')
----

=== Path Reconstruction

All algorithms use parent pointers to rebuild the path:

[source,python]
----
parent = {
    A: None,   # Starting point
    B: A,      # Reached B from A
    C: B,      # Reached C from B
    F: C       # Reached F from C
}

# Reconstruct backward then reverse
path = []
node = F
while node is not None:
    path.append(node)
    node = parent[node]
path.reverse()  # [A, B, C, F]
----

=== Visited vs Cost Tracking

- **BFS**: Uses `visited` set - never revisit a node
- **UCS/A***: Use `cost_so_far` dict - revisit if we find a better path

This is why UCS/A* guarantee optimality!

== Common Mistakes

1. **"BFS is faster"** - Wrong! BFS explores more nodes in dense networks
2. **"A* always works"** - Only if heuristic is admissible (never overestimates)
3. **"Heuristic must be exact"** - Wrong! It should underestimate
4. **"UCS and A* explore same nodes"** - Wrong! A* explores fewer due to heuristic

== Summary

- **BFS**: Simple but doesn't consider distances
- **UCS**: Optimal but explores many nodes
- **A***: Optimal AND fast (best choice for most cases)

Choose A* when you need the shortest path quickly!
